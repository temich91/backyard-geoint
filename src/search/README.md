# Поиск мест через FAISS

Модуль принимает **готовые векторы**, строит индекс и возвращает похожие фотографии
с координатами. PyTorch и модель не импортируются; извлечение признаков реализуется
отдельно. Фото напрямую этот CLI пока не принимает.

Используется точный `faiss.IndexFlatIP`. Векторы базы и запросов приводятся к `float32`
и L2-нормализуются, поэтому скалярное произведение равно косинусному сходству.
Обучать индекс и настраивать параметры приближённого поиска не требуется.

## Контракт с модулем извлечения векторов

Для базы нужны два файла:

1. `database.npy` — обычный числовой массив NumPy формы **(N, D)**, обычно `D = 4096`.
   Рекомендуемый тип — `float32`. Нулевые векторы, NaN и Inf недопустимы.
2. Исходный CSV базы, например `views_spatial/val_database.csv`, с **N строками данных**.
   Обязательные колонки: `image_id`, `path`, `lat`, `lon`. Остальные, в том числе
   `compass_angle`, `sequence_id`, `captured_at`, сохраняются в результатах.

**Вектор `embeddings[i]` должен соответствовать строке `i` CSV**, без заголовка и с нуля.
Нельзя сортировать, перемешивать или пропускать строки только в одном из файлов.
`ImageDataset` возвращает номер строки: извлекатель может записывать результат по этому
номеру. Если изображение не удалось обработать, лучше остановиться с ошибкой, а не
молча сдвигать привязку. Если отбор необходим, передайте согласованный CSV-поднабор.
Модуль проверяет количество строк и уникальность ID, но по самим векторам невозможно
обнаружить перестановку относительно CSV.

Для запросов нужен `queries.npy` формы **(Q, D)**. Для одного запроса допустим и `(D,)`.
Результаты возвращаются в порядке запросов; при оценке качества этот порядок должен
совпадать с CSV запросов. `.npz`, pickle и тензоры `.pt` не поддерживаются.

База и запросы должны использовать **одинаковые веса модели и предобработку**.
Для MixVPR это включает обрезку низа, resize и нормализацию, без случайных аугментаций
и с `model.eval()`. Рекомендуется передавать `--descriptor-id` — общую метку версии
весов и предобработки. При запросе переданная метка проверяется по индексу.
Это не автоматическая проверка весов: в самом `.npy` таких сведений нет.

## Установка

Зависимости уже есть в `pyproject.toml`. Для одного только поиска, без PyTorch:

```bash
pip install "numpy>=1.24,<2" "faiss-cpu>=1.8"
```

Команды ниже запускаются **из корня проекта**, рекомендуемая версия Python — 3.12.
Векторы в примерах должен заранее создать модуль извлечения признаков.

## Вариант Б: валидация

Строим индекс только по **валидационной базе**, а не по `train.csv`:

```bash
python -m src.search build \
  --embeddings artifacts/embeddings/val_database.npy \
  --metadata data/city_train/views_spatial/val_database.csv \
  --out artifacts/search/val-run01 \
  --descriptor-id mixvpr-run01-crop033-320
```

Выполняем поиск по валидационным запросам:

```bash
python -m src.search query \
  --index artifacts/search/val-run01 \
  --queries artifacts/embeddings/val_queries.npy \
  --top-k 10 \
  --descriptor-id mixvpr-run01-crop033-320 \
  --output artifacts/results/val-run01.json
```

Без `--output` JSON выводится в stdout. Для одного запроса сохраните в `.npy` его
вектор и передайте тот же `--queries`. `--top-k` должен быть положительным;
если он больше размера базы, возвращаются все кандидаты, без фиктивных ID `-1`.
При совпадающих сходствах порядок кандидатов не гарантируется.

После смены весов нужно заново извлечь векторы **и базы, и запросов**, затем перестроить
индекс. Нельзя сравнивать запрос от нового чекпоинта с базой от старого.

## Финальный тест

После выбора чекпоинта по валидации создаётся **отдельный** индекс:

```bash
python -m src.search build \
  --embeddings artifacts/embeddings/test_database.npy \
  --metadata data/district/views/database.csv \
  --out artifacts/search/test-run01 \
  --descriptor-id mixvpr-run01-crop033-320

python -m src.search query \
  --index artifacts/search/test-run01 \
  --queries artifacts/embeddings/test_queries.npy \
  --top-k 10 \
  --descriptor-id mixvpr-run01-crop033-320 \
  --output artifacts/results/test-run01.json
```

Тестовый район не используется для настройки модели или параметров поиска.

## Результаты

На каждый запрос выдаётся список `matches`, отсортированный по убыванию `similarity`:

```json
{
  "query_index": 0,
  "matches": [
    {
      "rank": 1,
      "index_id": 17,
      "similarity": 0.93,
      "cosine_distance": 0.07,
      "metadata": {
        "image_id": "1000021170809578",
        "path": "1000021170809578.jpg",
        "lat": 54.77,
        "lon": 56.06
      }
    }
  ]
}
```

- `index_id` — номер строки исходного CSV базы, начиная с нуля.
- `image_id` остаётся строкой, чтобы не терять точность больших ID Mapillary.
- `path` сохраняется как в CSV, относительно корня соответствующего датасета.
- `similarity` — косинусное сходство, больше — лучше. Это **не вероятность**.
- `cosine_distance = 1 - similarity` — расстояние в пространстве признаков,
  **не расстояние в метрах**. Географическую ошибку и Recall считает отдельный модуль оценки.
- Координаты первого кандидата можно использовать как простое предсказание местоположения.

## Python API

Можно строить индекс прямо в памяти — это пригодится для валидации после каждой эпохи:

```python
from src.search import PlaceIndex, load_embeddings, read_metadata

index = PlaceIndex.build(
    load_embeddings("artifacts/embeddings/val_database.npy"),
    read_metadata("data/city_train/views_spatial/val_database.csv"),
    descriptor_id="mixvpr-run01-crop033-320",
)

results = index.search(
    load_embeddings("artifacts/embeddings/val_queries.npy"),
    k=10,
    descriptor_id="mixvpr-run01-crop033-320",
)
for query_index, matches in enumerate(results):
    best = matches[0]
    print(query_index, best.index_id, best.metadata["lat"], best.metadata["lon"])

index.save("artifacts/search/val-run01")
restored = PlaceIndex.load("artifacts/search/val-run01")
```

Пустая база запрещена; пустой пакет запросов `(0, D)` возвращает пустой список.
Входные массивы при нормализации не изменяются. При одинаковой размерности, но разных
весах, несовместимость можно обнаружить только по переданной метке `descriptor_id`.

## Хранение и ограничения

Каталог индекса содержит согласованный набор:

```text
val-run01/
├── index.faiss       # нормализованные векторы
├── metadata.json     # метаданные в порядке ID FAISS
└── manifest.json     # версия формата, размерность, метка модели, SHA256 файлов
```

Сохранение публикует каталог целиком после записи. Существующий путь не перезаписывается:
для нового эксперимента задайте новый `--out`. Не переносите `index.faiss` отдельно от
остальных файлов. Загрузка проверяет контрольные суммы, тип индекса, размерность и
число метаданных; повреждённые или перепутанные файлы отклоняются.

**Загружайте только доверенные индексы.** Контрольные суммы обнаруживают случайную порчу,
но не делают чужие бинарные файлы FAISS безопасными.

Точный индекс хранит все векторы в оперативной памяти: примерно `N × D × 4` байт,
без учёта метаданных и временных копий при построении. Для больших баз оптимизацию
(например IVF) можно добавить отдельно, сравнив качество с этим точным базовым поиском.
Каталог `artifacts/` и файлы `*.faiss` исключены из Git.

## Проверки

```bash
python -m unittest discover -s tests -p 'test_search.py' -v
```

Тесты используют настоящую CPU-версию FAISS и синтетические векторы, проверяют совпадение
с прямым NumPy-поиском, сохранение привязки GPS, контроль целостности и команды CLI.
Модель, фотографии, GPU и токен Mapillary не нужны.
