# Датасет: сбор фото с Mapillary и загрузка в PyTorch

Эта часть проекта собирает датасет уличных фото с координатами и отдаёт его нейросети.
Все команды ниже запускаются **из корня репозитория**.

## Откуда данные

Снимки берутся с [Mapillary](https://www.mapillary.com) — открытой базы уличных фото (лицензия
CC BY-SA 4.0). В нашем городе это обычные кадры с видеорегистраторов и телефонов, 360-панорам нет.
Большинство снимков сделано в 2020–2021 годах.

Google и Яндекс не используем: их условия запрещают массовую выгрузку.


## Устройство датасета

```
data\district\
├── images\<две последние цифры id>\<id>.jpg   — сами фото, каждое ровно один раз
├── metadata.csv                               — все скачанные фото
├── views\
│   ├── database.csv   — база для поиска (FAISS)
│   ├── queries.csv    — запросы для проверки
│   ├── train.csv      — обучающая выборка для классификатора
│   ├── val.csv        — валидационная выборка
│   └── classes.csv    — список классов
└── tiles\             — кэш векторных тайлов Mapillary (служебное)
```

**Папки в `images\` ничего не значат.** Это просто последние две цифры id, чтобы в одной папке
не лежало 29 тысяч файлов. Где снято фото и для чего оно используется, смотрите в CSV.
Колонка `path` в CSV указана относительно корня датасета, например `images/78/1000021170809578.jpg`.

### Главное правило: база и запросы из разных поездок

Каждая поездка (`sequence_id`, одна запись регистратора) целиком попадает в одну из двух групп:

- **ref** (опорные, ~80%) — из них собираются база для поиска и обучающая выборка;
- **query** (запросные, ~20%) — только для проверки, в базу и обучение не попадают никогда.

Иначе запрос нашёлся бы по соседнему кадру той же поездки, снятому секундой раньше, и
точность была бы фальшиво высокой. **Не перемешивайте эти группы.**

### Колонки

Общие для всех CSV:

| колонка | что это |
|---|---|
| `path` | путь к фото |
| `image_id` | id снимка в Mapillary |
| `lat`, `lon` | координаты съёмки |
| `compass_angle` | куда смотрела камера, градусы (0 = север, 90 = восток) |
| `captured_at` | дата и время съёмки (UTC) |
| `sequence_id` | id поездки |

Дополнительно:

| колонка | где | что это |
|---|---|---|
| `role` | metadata | `ref` или `query` |
| `creator_id` | metadata | автор снимка в Mapillary (для указания авторства по лицензии) |
| `quality_score` | metadata | оценка качества от Mapillary, 0–1. Брали только ≥ 0.5 |
| `n_positives` | queries | сколько снимков базы считаются правильным ответом (см. ниже) |
| `class`, `class_idx` | train, val, queries | класс для классификатора; у запроса пусто, если такого класса нет в обучении |

`classes.csv`: имя класса, номер, координаты центра ячейки, направление и сколько в классе
снимков и поездок.

### Что считается правильным ответом

Запрос считается угаданным, если найденный снимок базы снят **не дальше 25 м** и смотрит
примерно туда же, **с разницей направления не больше 90°**. Метрика — Recall@1 / 5 / 10
(правильный ответ среди первых 1 / 5 / 10 найденных). Общий README проекта использует радиус
50 м: его можно посчитать по тем же координатам, датасет менять не нужно.

У каждого запроса в базе есть хотя бы один правильный ответ в пределах 25 м (а значит, и 50 м):
запросы без ответа отброшены. Сколько таких ответов, показывает `n_positives` (в районе
от 1 до 42, медиана 15). Чем меньше это число, тем запрос труднее.

### Классы (места для обучения)

Класс — это ячейка 50×50 м плюс направление камеры N / E / S / W. Например, `c027_049_N`:
ячейка в ряду 27 и столбце 49 сетки района, камера смотрит на север. Берутся только классы,
в которых есть хотя бы 4 разные поездки. Train и val внутри класса тоже разделены по поездкам.

Размер ячейки можно поменять без повторного скачивания:

```powershell
python .\src\data\build_dataset.py --bbox 56.046410 54.758362 56.087351 54.782870 --out data\district --views-only --class-cell 75
```

## Два варианта разделения на обучение и проверку

Какой использовать, решаем позже. Оба варианта используют одни и те же скрипты, и в обоих
запросы взяты из других поездок, чем база и обучение.

### Вариант А: по поездкам (уже готов)

Всё в `data\district\views\`. Обучение (`train.csv`, `val.csv`) и проверка (`database.csv`,
`queries.csv`) идут на одних и тех же улицах района, но по фото из разных поездок.
Проверяет: узнаёт ли модель **знакомые места на новых фото**. Это и есть сценарий
«система для одного города».

### Вариант Б: пространственный (нужно докачать город)

Модель учится на одних улицах, а проверяется на других, которых при обучении не было.
Проверяет: умеет ли модель **сравнивать фото незнакомых мест**. Оценка получается строже
и обычно ниже, чем в варианте А.

- **Тест:** район `data\district`, файлы `views\database.csv` и `views\queries.csv`.
  Ничего не меняется.
- **Обучение и валидация:** весь город, кроме района и полосы 100 м вокруг него, в отдельной
  папке `data\city_train`. Внутри неё город режется на квадраты 500×500 м, ~15% квадратов
  уходит в валидацию. Снимки ближе 50 м к границе между train и val выбрасываются, чтобы
  по разные стороны границы не оказались одни и те же дома.

```powershell
# 1. Сначала посчитать объём, ничего не скачивая (качаются только тайлы, ~285 штук)
python .\src\data\build_dataset.py --bbox 55.777588 54.672243 56.174469 54.844990 --out data\city_train `
    --exclude-bbox 56.046410 54.758362 56.087351 54.782870 --exclude-buffer 100 `
    --db-cell 25 --per-cell 2 --n-queries 3000 --spatial-views --dry-run

# 2. Если объём устраивает, та же команда без --dry-run
```

`--db-cell 25 --per-cell 2` — это предложение, а не проверенные цифры: в каждой ячейке класса
50 м должно набираться хотя бы 4 фото из разных поездок. Если объём после пункта 1 слишком
большой, увеличьте `--db-cell`. Если в выводе окажется мало классов, уменьшите его.
`--n-queries 3000` нужно, чтобы на валидацию (15% территории) пришлось несколько сотен
запросов.

Что появится в `data\city_train\views_spatial\`:

| файл | что это |
|---|---|
| `train.csv` | обучающие фото (только train-квадраты) с классом |
| `val.csv` | фото val-квадратов с классом (классы не пересекаются с train) |
| `classes.csv` | все классы, колонка `split` = `train` или `val` |
| `val_database.csv`, `val_queries.csv` | база и запросы для расчёта Recall на валидации |

У запросов в `val_queries.csv` `n_positives` пересчитано по `val_database.csv`. Папка
`views\` в `data\city_train` тоже создаётся (вариант А для города), для варианта Б она не нужна.

Параметры сплита можно менять без перекачки:
`--views-only --spatial-views --val-block 1000 --val-buffer 50 --val-frac 0.15`.
`--val-buffer` должен быть не меньше 25 м (радиуса правильного ответа).

## Основные параметры `build_dataset.py`

Полный список: `python .\src\data\build_dataset.py --help`.

| параметр | по умолчанию | смысл |
|---|---|---|
| `--bbox` | — | область `MIN_LON MIN_LAT MAX_LON MAX_LAT` |
| `--out` | `data\geo` | куда сохранять |
| `--db-cell` | 15 | шаг базы, м |
| `--per-cell` | 2 | сколько снимков базы на ячейку и направление (из разных поездок) |
| `--n-queries` | 1000 | сколько запросов |
| `--min-quality` | 0.5 | порог `quality_score` |
| `--max-side` | 512 | размер длинной стороны фото, px |
| `--dry-run` | | только посчитать объём |
| `--views-only` | | пересобрать CSV без скачивания |

Параметры отбора (`--db-cell`, `--per-cell`, `--min-quality` и т.п.) влияют на то, *какие*
фото скачиваются. Если менять их на уже скачанном датасете, скрипт докачает новые фото.

Весь город (bbox `55.777588 54.672243 56.174469 54.844990`) — 12.4 млн снимков на Mapillary.
Пробный прогон для варианта Б (город без района, `--db-cell 25 --per-cell 2 --n-queries 3000`)
показал 305 920 фото: около 15 ГБ и 8–12 ч загрузки. Сильно увеличивать `--db-cell` не стоит:
на место 50 м перестанет набираться 4 фото из разных поездок. Чтобы уменьшить объём, лучше
взять bbox поменьше или `--max-side 384` (вдвое меньше места, время почти то же).

## Загрузка данных в PyTorch: `vpr_dataset.py`

Модуль превращает строки CSV в то, что ест нейросеть: открывает фото, **обрезает нижнюю треть**
(приборная панель), приводит к 320×320, нормализует как для сетей с весами ImageNet. При
обучении добавляет лёгкие аугментации: яркость, контраст, небольшой случайный кроп.
Отражения по горизонтали нет: оно меняет местами стороны улицы.

```powershell
pip install torch torchvision pillow
```

- **`PlacesDataset`** — для обучения (MixVPR). Один элемент — одно место (класс из `train.csv`)
  и 4 его фото, по возможности из разных поездок. Фото выбираются заново каждую эпоху.
  `places_loader(ds, places_per_batch=32)` собирает батч 32 места × 4 фото = 128 фото,
  у фото одного места одинаковая метка.
- **`ImageDataset`** — для поиска и оценки: одно фото без меток, в порядке строк CSV.
  Номер вектора в FAISS = номер строки, а координаты лежат в `ds.rows[i]`.

```python
from src.data.vpr_dataset import PlacesDataset, ImageDataset, make_transform, places_loader, image_loader

train = PlacesDataset("data/district", "views/train.csv", img_per_place=4)
for images, labels in places_loader(train, places_per_batch=32):   # (128, 3, 320, 320), (128,)
    ...

db = ImageDataset("data/district", "views/database.csv")
for images, idx in image_loader(db, batch_size=64):
    ...                                    # векторы → FAISS; координаты: db.rows[i]["lat"], ["lon"]
```

Для варианта Б вместо `views/...` используйте `views_spatial/train.csv`,
`views_spatial/val_database.csv` и `views_spatial/val_queries.csv`.

На Windows загрузка в несколько потоков (`num_workers > 0`) работает только внутри
`if __name__ == "__main__":`.

Проверить, что всё читается, и посмотреть, что видит сеть:

```powershell
python .\src\data\vpr_dataset.py --root data\district --views views
```

Скрипт сохранит `preview_views_train.jpg`: одна строка — одно место, 4 фото из разных поездок.

В варианте А 317 мест из 2618 пропускаются: после выделения части поездок в val у них
в train остаётся меньше 4 фото. Можно поставить `img_per_place=3`.
